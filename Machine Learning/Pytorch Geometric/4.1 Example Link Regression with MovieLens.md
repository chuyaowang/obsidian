## Mapping movieID and userID to a consecutive range

Mapping original IDs to a consecutive range starting from zero is a strict requirement for how graph neural networks (GNNs), particularly in PyTorch Geometric, structure and process data under the hood.

Here are the primary reasons why this step is necessary:

### 1. Direct Tensor Indexing

In PyTorch Geometric, your nodes' features are stored in continuous 2D tensors (matrices), where each row corresponds to a single node. The `edge_index` doesn't just store abstract ID labels; it stores the **actual row indices** used by PyTorch to look up those nodes' features during the message-passing phase of training.

By mapping the IDs, the code guarantees that `mappedUserId == 0` points exactly to the 0th row of the `user_features` matrix, and `mappedMovieId == 14` points exactly to the 14th row of the `movie_features` matrix.

### 2. Memory Efficiency (Avoiding Wasted Space)

Real-world IDs almost always have gaps. For instance, due to deleted users or missing data, you might have user IDs like `[1, 15, 900]`.

If you used these raw, original IDs in the `edge_index`, PyTorch would be forced to allocate a feature matrix with at least 901 rows just to be able to look up index `900`. This would leave 898 rows completely empty and uninitialized, wasting massive amounts of memory and compute resources. By mapping them to a consecutive range `[0, 1, 2]`, you ensure your feature matrix has exactly 3 rows, making it perfectly compact.

### 3. Zero-Based Indexing

Python and PyTorch use 0-based indexing. Datasets like MovieLens typically start their IDs at 1. If you try to use an original ID equal to `len(nodes)` to index into a feature matrix of size `len(nodes)`, the code will crash with an `IndexError: index out of bounds`. Compressing everything into a `[0, num_nodes - 1]` range safely prevents this.

``` python
HeteroData(

	movie={ x=[9742, 404] },

		edge_label_index=[2, 10084], }, 
	(movie, rev_rates, user)={ edge_index=[2, 90762] } ))
```

Here is a breakdown of how the `RandomLinkSplit` works and why those specific numbers appear in your `test_data`.

### 1. How the Train, Val, and Test Data is Split

In a node-level task, you split the _nodes_. But in a link prediction or regression task like this one, you split the **edges**.

Your original dataset has exactly **100,846** rating edges. The `RandomLinkSplit` function divides these edges based on the ratios you provided:

- **Validation Set (`num_val=0.1`)**: 10% of the edges randomly selected (approx. **10,084** edges).
- **Test Set (`num_test=0.1`)**: 10% of the edges randomly selected (approx. **10,084** edges).
- **Training Set**: The remaining 80% of the edges (approx. **80,678** edges).

### 2. Why `test_data` has 90,762 edges but only 10,084 labels

This mismatch highlights a fundamental concept in Graph Neural Networks: the difference between **message passing edges** (`edge_index`) and **supervision edges** (`edge_label_index`).

To predict a user's rating for a movie, the GNN needs to look at the neighborhood of that user and that movie (message passing). However, if the exact edge we are trying to predict is _included_ in the message passing step, the model will essentially "cheat" (data leakage) because the target node will directly see the source node's rating.

To prevent this, PyTorch Geometric constructs the `edge_index` for each split differently:

- **`train_data`**:
    - `edge_label_index` (what to predict) = 80,678 training edges.
    - `edge_index` (what to use for message passing) = 80,678 training edges. _(PyG handles the cheating internally during training by predicting on the fly, or you can use specialized message passing layers)._
- **`val_data`**:
    - `edge_label_index` = 10,084 validation edges.
    - `edge_index` = **80,678** edges. When evaluating validation edges, the model is _only_ allowed to use the training edges for message passing. It hides the validation edges so it doesn't cheat.
- **`test_data`**:
    - `edge_label_index` = 10,084 test edges.
    - `edge_index` = **90,762** edges. When evaluating the final test set, the model is allowed to use **both the training edges AND the validation edges** for message passing (80,678 + 10,084 = 90,762). This gives the model the richest possible graph structure to make its final predictions, while safely keeping the 10,084 test edges completely hidden.

So, in `test_data`, there are **10,084** questions to answer (`edge_label`), and the model uses a graph made of **90,762** known connections (`edge_index`) to figure out the answers!

## Negative sampling

In graph neural networks, **negative sampling** is the process of artificially generating "fake" edges (connections) between nodes that do not actually exist in your dataset.

To understand why this is used, it helps to look at the two types of edges in a graph:

- **Positive edges:** Connections that actually exist in your data (e.g., User A watched and rated Movie B).
- **Negative edges:** Connections that do _not_ exist in your data (e.g., User A has never seen Movie C).

### Why is `neg_sampling_ratio=0.0` here?

In this specific notebook, you are performing **Link Regression**—meaning your goal is to predict the exact star rating (e.g., 4.5 stars) a user would give to a movie.

Because you are trying to predict a specific rating value, you can only train your model on edges where a rating _already exists_ (the positive edges). If you were to randomly sample negative edges (movies the user hasn't seen), there would be no ground-truth rating to train the model against. A missing rating doesn't mean the user gives it 0 stars; it just means it's unknown. Therefore, the ratio is set to `0.0` to tell PyTorch Geometric to skip generating fake edges entirely.

### When would you use a ratio > 0.0?

If you were performing **Link Prediction** (a binary classification task where you just want to predict _if_ a user will watch a movie or not, regardless of the rating), you would typically set `neg_sampling_ratio=1.0` (or another positive value).

In that scenario, the model needs to see both examples of movies the user watched (Label = 1) and movies the user didn't watch (Label = 0) so it can learn to distinguish between the two.

## Model design

### 1. The meaning of `(-1, -1)` in `SAGEConv`

In PyTorch Geometric, the first argument to a convolution layer like `SAGEConv` is usually `in_channels` (the number of input features). Here we have two set of nodes (movie and user). So each element in the tuple represent the `num_features` for each node type.

When you pass `(-1, -1)`, you are telling PyTorch Geometric to use **lazy initialization**.

- Instead of you having to manually specify the exact input dimensions, the layer will automatically infer the input sizes during the very first forward pass based on the shape of the data it receives.
- The tuple format `(source_dim, target_dim)` is used because this is a bipartite/heterogeneous interaction. In our dataset, User nodes and Movie nodes have different initial feature sizes (e.g., User features might be an identity matrix of size 611, while Movie features are a concatenation of genres and BERT embeddings of size 404). By using `(-1, -1)`, the model gracefully accepts that the source node and destination node in a message-passing step have different, undetermined initial sizes.

### 2. The Data Flow

The overall data flow through the model happens in two main stages: **Encoding** (learning graph-aware node embeddings) and **Decoding** (predicting the link relationship).

Here is the step-by-step journey of the data when you call `model(x_dict, edge_index_dict, edge_label_index)`:

#### Step 1: The Input

The `Model` receives three dictionaries/tensors:

- **`x_dict`**: The raw node features for each node type (Users and Movies).
- **`edge_index_dict`**: The graph structure detailing how Users are connected to Movies (and vice-versa).
- **`edge_label_index`**: A `[2, num_queries]` tensor containing the specific pairs of `(user, movie)` that we actually want to predict a rating for in this batch. For example, how does user 0 rate `movie 14`.

#### Step 2: The Encoder (`GNNEncoder` + `to_hetero`)

- The raw `x_dict` and `edge_index_dict` are passed into `self.encoder`.
- Because we wrapped `GNNEncoder` with `to_hetero(...)`, PyG automatically duplicates the `SAGEConv` layers under the hood for every edge type defined in `data.metadata()`.
- **Layer 1 (`conv1`)**: For every user, the model aggregates the features of all the movies they have rated. For every movie, it aggregates the features of all the users who rated it. It applies a ReLU activation. The node dimensions are transformed from their original uneven sizes to exactly `hidden_channels` (32).
- **Layer 2 (`conv2`)**: The process repeats, but now it's aggregating the _updated_ 32-dimensional features from Layer 1. This allows a user to learn not just from the movies they watched, but indirectly from the _other users_ who watched those same movies (2-hop neighborhood).
- **Output of Encoder**: The encoder returns `z_dict`, a dictionary containing the new, heavily enriched 32-dimensional embeddings for all users and all movies.

#### Step 3: The Decoder (`EdgeDecoder`)

- The `z_dict` (enriched embeddings) and `edge_label_index` (the target pairs to predict) are passed to the `self.decoder`.
- **Feature Extraction**: The decoder splits `edge_label_index` into `row` (user indices) and `col` (movie indices). It then looks up the specific 32-dimensional user embedding and 32-dimensional movie embedding from `z_dict`.
- **Concatenation**: It glues these two embeddings together side-by-side (`torch.cat(..., dim=-1)`), resulting in a single 64-dimensional vector representing that specific user-movie pair.
	- For the input, there are 64 columns, 32 from the movie embeddings, 32 from the user embeddings. The row number is the number of predictions to be made. For training, the decoder tries to predict for all 80678 training edges. For validation, the matrix contains 10084 validation edges. For testing, the matrix contains 10084 testing edges.
- **MLP Prediction**: This 64-dimensional vector is passed through a simple Multi-Layer Perceptron (MLP):
    - `lin1` reduces it from 64 to 32 dimensions (followed by a ReLU activation).
    - `lin2` reduces it from 32 to exactly **1** dimension.
- **Final Output**: `z.view(-1)` flattens the output into a 1D tensor of predicted star ratings (e.g., `[4.2, 3.1, 4.8, ...]`).
